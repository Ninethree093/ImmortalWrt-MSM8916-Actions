# ImmortalWrt-MSM8916-Actions 适配实录

> 把一个「多机型 OpenWrt 云编译模板」改造成「只做高通 msm8916、可选分支/稳定版、内核自动跟随源码」的独立项目，中间踩过的坑和可复用的方法都在这里。
>
> 仓库：<https://github.com/Ninethree093/ImmortalWrt-MSM8916-Actions>

---

## 1. 起点与目标

**起点**：`Ninethree093/Actions-OpenWrt` 是 fork 自 `xuxin1955/Actions` 的多机型云编译模板，同时维护 mt7620 / mt7621 / mt7628 / XG-040G / sy108 / msm8916 等多套 target，源码固定接 `immortalwrt`。

**目标**（按需求演进）：

| # | 需求 | 结果 |
| --- | --- | --- |
| 1 | 只保留 msm8916 | 删掉其它 target、config、工作流 |
| 2 | 源码可选 immortalwrt 的 24.10 及以后分支 | `source` 下拉 |
| 3 | 能选稳定版正式版号（不是 SNAPSHOT） | 下拉里放 `v25.12.2` 这类 tag |
| 4 | 机型可选 | `device` 下拉，13 个机型 |
| 5 | 内核用分支自带的，不手填 | 自动探测 |
| 6 | 编译要能过，固件要能开机 | 见第 4 节 14 个问题 |
| 7 | 发布质量（软件源、默认插件、缓存、许可证） | 见第 5 节 |

## 2. 最终形态

### 2.1 目录

```
.github/workflows/
  Build_imm_高通_8916.yml     固件编译（主力）
  Build_bootloader_msm8916.yml lk2nd 引导编译
config/                       13 个机型的 .config
scripts/msm89xx/              msm8916 的 target / package / toolchain 源码
scripts/files-8916/           打进固件的 /etc 覆盖（网络、软件源、modem 初始化）
diy-part1.sh                  feed 安装前：打入 target、修内核、钉 feed、补 config
diy-part2.sh                  feed 安装后：改 IP/主题、剥离依赖、生成软件源、打补丁
check-patches.sh              编译前：backports 补丁预演
flash.zip                     首次线刷包
```

### 2.2 工作流结构

```
setup job（ubuntu-latest，秒级）
  └─ 解析机型 → 输出 JSON 数组
        ↓ fromJSON 喂给矩阵
build job × N（ubuntu-24.04，串行 36 步）
  ├─ 选源码 → 校验分支/tag → 算缓存分支
  ├─ 克隆源码 → 探测内核 → DIY_P1 → feeds → DIY_P2
  ├─ defconfig → 配置校验 → 下载 → 补丁预检 → make
  └─ 整理产物 → 发 Release → 清理旧 run / 旧缓存
```

**为什么用 setup + `fromJSON`**：`strategy.matrix` 不能直接读 `workflow_dispatch` 的输入，必须用一个前置 job 把输入转成 JSON 数组再喂给矩阵。好处是选 1 个机型只跑 1 个 job，选 `all` 就是 13 个并行。

### 2.3 输入项（最终只有 2 个下拉 + 1 个开关）

| 输入 | 类型 | 取值 |
| --- | --- | --- |
| `source` | 下拉 | `openwrt-25.12`（默认）、`master`、`v25.12.2`、`v25.12.1`、`v25.12.0` |
| `device` | 下拉 | `all`（默认）+ 13 个机型 |
| `ssh` | 布尔 | 调试用，默认关 |

早期版本有过 `branch` / `release` / `branch_custom` / `kernel` / `devices_custom` 五个输入，后来全部合并删减——**输入项越少，出错面越小**：分支和 tag 合成一个下拉、内核改成自动、自定义输入全删。

## 3. 适配过程（6 个阶段）

### 阶段 1：裁剪到 msm8916

- 删掉其它 SoC 的 `target/linux/*`、`package/`、`toolchain/` 与 `config/*.config`
- 删掉对应的矩阵列、其它工作流
- `env.ALL_DEVICES` 与 `inputs.device.options` 两处同步维护（矩阵是动态生成的，不用动）

### 阶段 2：接入 immortalwrt 多分支

关键点：**msm8916 的 target 不是 immortalwrt 官方 target**，是项目自带的一套 `target/linux/msm89xx`，靠 `diy-part1.sh` 在克隆后覆盖进去。所以它天然会跟上游分支「错版」——官方 target 里有的常量、头文件、伪包，它可能没有。

### 阶段 3：机型下拉

`setup` job 解析名单 → 校验 `config/<机型>.config` 存在 → 输出 JSON → 矩阵。

### 阶段 4：内核自动跟随

target 的 `KERNEL_PATCHVER` 写死 `7.3`，但 25.12 只有 6.12、24.10 只有 6.6。做法见 5.1。

### 阶段 5：让 25.12 编过并开机

这一阶段占了全部工作量的大头，见第 4 节。

### 阶段 6：发布质量

- 默认插件：关 `luci-app-simadmin`、开 `luci-app-openclash`
- 固件软件源按版本生成（5.6）
- 缓存治理与并发锁（5.7）
- 改名、许可证与 fork 声明

## 4. 问题档案

### 4.1 总表

| # | 现象（日志关键字） | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `ls: cannot access '.config'` | 校验步骤查了仓库根的 `.config` | 改查 `openwrt/.config`，并加 `CONFIG_TARGET_msm89xx=y` 断言 |
| 2 | `14 patch(es) failed on backports-7.2` | `scripts/msm89xx/package` 把 master 的 `mac80211/Makefile` 盖到了 25.12 上 | 还原分支自带 Makefile，只补一行依赖 |
| 3 | `0104-uapi-128bit.patch` `Hunk #1 FAILED` | 补丁只对 7.x 有效，6.x 的 uapi 本来就是 `__uint128_t` | 按内核主版本条件删除补丁 |
| 4 | `pathspec 'openwrt-25.12' did not match any file(s)` | feeds 钉版用了 `^`（钉 commit），实际点是分支 | 改用 `;` |
| 5 | `input-support (no such package): required by rmtfs` | `*-support` 是 feature 伪包，只有 master 的 `modules/*.mk` 里定义 | 树里没有定义就从依赖里剥掉 |
| 6 | `dt-bindings/clock/qcom,dsi-phy-28nm.h: No such file` | 该头文件 6.15 才进内核 | 把两个宏内联进 dtsi |
| 7 | `msm8916.dtsi:1988.28-29 syntax error` | 真凶是上一行 `RPMPD_VDDCX`：6.18 才改的名，老内核没有 | `#ifndef` 别名兜底 |
| 8 | 编译通过但**不开机**（拿不到后台 IP） | `config-6.12` 残缺：`CONFIG_SQUASHFS`、`OVERLAY_FS`、`QCOM_Q6V5_MSS`、`QCOM_WCNSS_PIL`、`CRYPTO_AES/CTR/GCM` 都没开 | 用 `config-7.3` 合并补全 |
| 9 | `ERROR: unzip-6.0-r9: trying to overwrite usr/bin/unzip owned by busybox` | 开 openclash 后拉进独立 `unzip` 包，与 busybox applet 抢文件 | 关 `CONFIG_BUSYBOX_CONFIG_UNZIP` |
| 10 | `glib2-gobject is missing dependencies: libffi.so.8` | feed 没跟分支走，拿到 master 的 packages（libffi 已挪进 base） | feed 钉到同名分支 |
| 11 | 同上，但只在**选 tag** 时复现 | feeds 钉版逻辑只认分支，tag 查 `--heads` 查不到 → 退回 master feed | tag 映射成对应分支再钉 |
| 12 | master 构建在 toolchain 阶段挂 `0104` | master 内核已是 6.18，补丁仍在硬套 | 阈值从「< 6.16 跳过」改为「仅 7.x 保留」 |
| 13 | 构建无日志、job 步骤全是 `None`、API 报 `BlobNotFound` | 两次构建**并发**跑，抢同一个缓存 key，runner 中途掉线 | 加 `concurrency` 串行 + 治理缓存 |
| 14 | 固件里软件源指向 `snapshots` + `targets/armsr/armv8` | `files-8916` 里写死了 pku 快照地址 | 按 `REPO_BRANCH` 生成软件源 |
| 15 | `defconfig 之后 .config 里没有 CONFIG_TARGET_msm89xx=y` | 24.10 只有 6.6 内核，与按 7.3/6.12 写的 target 不兼容，kconfig 直接把 target 裁掉 | 移除 24.10 选项，并在第一步显式拦截 |

### 4.2 三个最难的

#### （1）backports 补丁大面积失败

```
14 patch(es) failed on backports-7.2
```

看起来是「补丁不兼容」，实际是**版本被覆盖**：`cp -rf scripts/msm89xx/package/.` 把作者在 master 上写的 `package/kernel/mac80211/Makefile`（`PKG_SOURCE_VERSION:=7.2`）盖到了 25.12 树里，而 25.12 需要的是 `PKG_VERSION:=6.18.55`。源码版本一变，它的整套补丁自然全对不上。

**修法**：

```bash
git checkout -- package/kernel/mac80211/Makefile   # 还原分支自带
# 只补真正需要的那一行依赖
sed -i 's/^\([[:space:]]*DEPENDS+= .*hostapd-common\)$/\1 +kmod-crypto-arc4/' ...
```

同时让 `check-patches.sh` 兼容两种字段名（新版 `PKG_SOURCE_VERSION`、旧版 `PKG_VERSION`），把「编译到一半才发现补丁坏」提前成「编译前预检」。

> 教训：**覆盖上游文件时要区分「这个文件是分支相关的，还是跨分支通用的」**。Makefile 里的 `PKG_*` 版本号属于前者。

#### （2）编译通过但不开机

这是最隐蔽的一类：CI 全绿、产物齐全、刷进去就是起不来。

现象是 `系统起不来 → 拿不到 192.168.10.1`。根因不在代码而在 **target 的 kernel config**：`config-6.12` 是从更早版本抄来的，缺了 `CONFIG_SQUASHFS`（根文件系统解不开）、`OVERLAY_FS`、`QCOM_Q6V5_MSS`/`QCOM_WCNSS_PIL`（modem/WiFi 固件加载）、`CRYPTO_AES/CTR/GCM`（WiFi 加密）。

**修法**（`diy-part1.sh`）：以 `config-7.3` 为基底，把 `<KP>` 独有的项追加回去，交给 kconfig 在 `defconfig` 时丢弃新内核才有的符号：

```bash
if [ -f "$CFG" ] && [ -f "$REF" ] && ! grep -q '^CONFIG_SQUASHFS=y' "$CFG"; then
    cp "$REF" "$CFG.merged"
    # 逐行提取 <KP> 独有的 key，追加
    ...
    mv "$CFG.merged" "$CFG"
fi
```

> 教训：**「能编译」和「能启动」是两回事**。换内核时必须核对根文件系统、overlay、固件加载、加密这几类基础设施选项。

#### （3）runner 掉线不是编译错误

```
build job 从第 26 步起全部 None
API: 404 BlobNotFound（日志根本不存在）
```

两次失败都发生在**和另一次构建重叠**的时间段：

```
#24  00:55 → 01:53  取消
#25  01:49 → 02:41  失败   ← 与 #24 重叠 4 分钟
#26  02:27 → 03:32  失败   ← 与 #25 重叠 14 分钟
#27  04:55 → 07:35  成功   ← 独占
```

缓存侧也印证：同一个 `dl` 缓存 key 存了两份（2222 MB 和 2700 MB）——**只有两次构建并发保存同一个 key 才会这样**。

**修法**：

```yaml
concurrency:
  group: ${{ github.workflow }}
  cancel-in-progress: false    # 后来的排队，而不是并发
```

> 教训：**先看「哪些步骤没跑」，再看「报了什么错」**。整段 `None` + 日志缺失 = 基础设施问题，改代码没用。

## 5. 可复用的适配方法

### 5.1 内核版本探测

target 的 `KERNEL_PATCHVER:=7.3` 是写死的，但上游分支的内核各不相同。做法：**克隆后、覆盖 target 前**，先读上游树里有什么。

```bash
AVAIL=$(ls target/linux/generic/kernel-* | sed 's#.*/kernel-##' | sort -V)
# 有 target 要求的 7.3 就用 7.3，否则用上游自带的最新版本
case " $AVAIL " in *" 7.3 "*) PICK=7.3 ;; *) PICK=$(echo $AVAIL | tail -1) ;; esac
sed -i "s/^KERNEL_PATCHVER:=.*/KERNEL_PATCHVER:=$PICK/" target/linux/msm89xx/Makefile
```

时序很关键：**必须在 `diy-part1.sh` 之前探测**，因为 DIY_P1 会把 target 自带的 `kernel-7.3` 拷进来，之后就分不清哪些内核是分支原生的了。

| 源码 | 自动选的内核 |
| --- | --- |
| `master` | 6.18 |
| `openwrt-25.12` / `v25.12.x` | 6.12 |
| `openwrt-24.10` / `v24.10.x` | 6.6 |（**已移除**：defconfig 会把 target 裁掉，见 4.1 #15） |

### 5.2 feeds 钉版

**问题**：feed 不钉版本 → 拿到 master 的包 → 与分支的 base 不匹配（典型：`libffi` 消失 → `glib2` 打包失败）。

**语法**：`scripts/feeds` 里 `split(/;/)` 取分支，所以分隔符是 `;`：

```
src-git packages https://github.com/immortalwrt/packages.git;openwrt-25.12
```

> `^` 是钉 commit，用错了会 clone 完再 checkout 一个不存在的 ref，报 `pathspec ... did not match`。

**tag 要映射成分支**：选 `v25.12.2` 时，feed 需要的仍是 `openwrt-25.12`。`git ls-remote --heads` 查 tag 查不到，会静默退回 master feed，问题就以另一种面貌出现（又是 `libffi`）。

```bash
case "$BR" in
  v[0-9]*) _ver=$(echo "$BR" | sed -E 's/^v([0-9]+\.[0-9]+).*/\1/'); BR="openwrt-$_ver" ;;
esac
```

### 5.3 跨内核版本兼容层

适配老内核（6.6/6.12）与较新 target（按 7.3 写）的三种手法：

| 手法 | 适用 | 例子 |
| --- | --- | --- |
| **按版本条件删除补丁** | 补丁只对某个大版本有效 | `0104-uapi-128bit.patch` 仅 7.x 保留 |
| **头文件内联** | 头文件在新内核才加入 | `dsi-phy-28nm.h` 只有两个宏，直接 `#define` |
| **`#ifndef` 别名** | 常量/宏在新内核改名，值不变 | `RPMPD_VDDCX` → `MSM8916_VDDCX` |

第三种最优雅，因为**新内核上自动失效**：

```c
#ifndef RPMPD_VDDCX
#define RPMPD_VDDCX MSM8916_VDDCX
#endif
```

### 5.4 feature 伪包依赖剥离

新版 OpenWrt 把一批「功能开关」做成伪包（`define Package/input-support` 之类），只有 master 有。但 feeds 里的包是按 master 写的：

```
DEPENDS:=+input-support +libudev-zero ...
```

老分支上镜像组装就报 `input-support (no such package)`。

做法是**先查再剥**，不要硬编码包名：

```bash
for feat in audio-support video-support input-support dvb-support scanner-support accel-support; do
    grep -rqs "Package/$feat" package/ && continue      # 本分支有这个伪包，跳过
    grep -rl --include=Makefile "+$feat" feeds package | xargs -r sed -i "s/ *+$feat//g"
done
```

### 5.5 固件软件源按版本生成

**问题**：`files-8916` 里写死了 `mirrors.pku.edu.cn/immortalwrt/snapshots/...`，从 `v25.12.2` 编出来的固件也指向快照，版本对不上。

**修法**：构建时按 `REPO_BRANCH` 生成（apk 与 opkg 两套都写）：

| 源码 | 软件源根 |
| --- | --- |
| `v25.12.2` | `.../releases/25.12.2` |
| `openwrt-25.12` | `.../releases/25.12-SNAPSHOT` |
| `v24.10.6` | `.../releases/24.10.6`（已移除） |
| `openwrt-24.10` | `.../releases/24.10-SNAPSHOT`（已移除） |
| `master` | `.../snapshots` |

**只写 `aarch64_generic` 的 5 个通用源**，不写 target 源，原因实测过：

| 地址 | 结果 |
| --- | --- |
| `releases/25.12.2/packages/aarch64_generic/base/packages.adb` | ✅ 200 |
| `releases/25.12.2/targets/msm89xx/msm8916/packages/...` | ❌ 404（自建 target 上游没发布） |
| `releases/25.12.2/targets/armsr/armv8/packages/...` | ✅ 200 但**不能用**（armsr 的 kmod 装到 msm8916 上会坏） |

### 5.6 缓存策略

| 项 | 做法 | 原因 |
| --- | --- | --- |
| 缓存键跟随分支 | tag 映射成 `openwrt-25.12` 再算 key | 让 tag 构建复用分支的 ccache |
| **不用 dl 缓存** | 每次重新 `make download` | 2.7 GB 只省约 7 分钟，还容易出现重复 key |
| ccache 只留 3 份 | 构建后删旧的 | key 带 `run_id`，每次新增 0.4~0.8 GB，会撞 10 GB 上限 |
| 并发锁 | `concurrency` 串行 | 并发抢缓存 key，runner 会掉线 |

清理前的实际数据：`10 条 / 8.02 GB`，其中两条同 key 的 dl 缓存 2222 MB + 2700 MB。清理后 `5 条 / 1.78 GB`。

### 5.7 发布流水线

```
Organize files → Prefix common → Upload artifact → Generate tag → Generate list → Release
```

- Release 标签：`MSM8916-<源码>-<日期>-V<run_number>`
- 正文自动生成：编译时间、机型、版本类型（稳定版/快照版）、源码、内核、管理地址、刷机提示、本次实际包含的 `luci-app-*` 清单
- 产物 9 个：`sysupgrade.bin`、`system.img`、`boot.img`、`manifest`、3 个 buildinfo、`profiles.json`、`sha256sums`

## 6. 排错方法论

### 6.1 读 CI 日志的层次

按「从粗到细」四层往下钻，不要一上来就翻几千行：

1. `##[error]` —— 找到失败的那一步
2. `make: *** [.../world] Error N` —— 找到失败的 make 目标
3. `ERROR: package/feeds/xxx failed to build` —— 找到失败的包
4. 包内部的 `patch ... FAILED` / `fatal error:` / `missing dependencies` —— 真正的原因

**经验**：apk 装包阶段的失败，真正的错误行往往在「`1 error; 386.3 MiB in 411 packages`」**上方几十行**，而且不在 `Installing (...)` 里，要过滤掉那些行再找。

### 6.2 区分「真失败」和「假失败」

| 特征 | 判断 |
| --- | --- |
| 有具体编译错误、错误行在包里 | 真失败，改代码 |
| 步骤全是 `None`、没有日志、API 返回 `BlobNotFound` | runner 掉线，基础设施 |
| `conclusion: cancelled` | 手动取消 |
| 日志只有 setup、没有 build | build job 没跑起来或被取消 |

### 6.3 本地验证手法

不是每个改动都要推 CI 跑 2 小时。以下都能在本地秒级验证：

- **YAML**：`yaml.safe_load` 解析 + 断言 inputs/步骤数
- **Shell**：把步骤从 YAML 里抽出来，替换掉 `${{ }}` 占位，`sh -n` 查语法
- **逻辑**：用假的 `git` 函数 + 临时目录跑片段（例如 feeds 钉版、软件源生成、内核选择），断言输出
- **文件**：推送后用 GitHub Contents API 按 commit sha 比对本地与线上（注意 `raw.githubusercontent.com` 有 CDN 缓存，会返回旧内容）

### 6.4 版本相关问题的通用排查顺序

换一个分支/tag 后编译失败，按这个顺序查：

```
内核版本对不对 → feeds 钉没钉 → 补丁适用不适用 → 依赖包在不在 → 配置项全不全
```

## 9. 新增机型 / 分支 / 内核的配方

**加机型**

1. 放 `config/<机型>.config`
2. `env.ALL_DEVICES` 加名字
3. `inputs.device.options` 加名字

矩阵是动态生成的，不用动。

**加分支或 tag**

1. `inputs.source.options` 加一项
2. 若 feed 侧有同名分支，钉版会自动生效

**换内核**

不用手动指定：克隆后会探测源码自带的 `target/linux/generic/kernel-*`，优先用 target 要求的版本，没有就用最新的那个。真正要做的只有一件事——**确认新内核下补丁/头文件/宏的兼容层还够用**（参考 5.3）。
